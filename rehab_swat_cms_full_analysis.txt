PART 3: CRITICAL BUGS & SECURITY ISSUES IN EXISTING CODE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These must be fixed before giving this to ANY client. They are not features — they
are broken or dangerous things in the current code.

BUG 1 — HARDCODED SECRET KEY (CRITICAL SECURITY)
  File: auth.py, line 4
  Code: SECRET_KEY = "rehab-swat-super-secret-key-change-in-production-2024"
  Problem: The JWT secret key is hardcoded as a plaintext string in source code.
           Anyone with access to the code can forge any JWT token and log in as
           any user including the admin. This is a textbook auth bypass.
  Fix: Move to environment variable. SECRET_KEY = os.getenv("JWT_SECRET_KEY")
       Generate with: openssl rand -hex 32

BUG 2 — SQLITE INSTEAD OF POSTGRESQL (WRONG DATABASE)
  File: database.py (not shown but .db file confirms SQLite)
  Problem: Blueprint specifies PostgreSQL 16 with row-level security, JSONB,
           and full-text search. The actual database is SQLite. SQLite has:
           - No row-level security
           - No JSONB (stores as text)
           - No concurrent write support (one writer at a time — clinic has 5 users)
           - No timezone-aware datetime handling
           - No full-text search indexes
  Fix: Must migrate to PostgreSQL before ANY production use.

BUG 3 — NO REFRESH TOKEN (AUTH DESIGN FLAW)
  File: auth.py
  Problem: Blueprint specifies JWT access + refresh token rotation. Only access
           token is implemented. 8-hour expiry is dangerously long for a medical
           system. If a token is stolen, the attacker has 8 hours of unrevokable
           access to all patient data.
  Fix: Implement refresh token with 15-min access token + 7-day refresh token.
       Store refresh tokens in DB to allow revocation.

BUG 4 — PATIENT CREATE ENDPOINT HAS NO AUTH GUARD
  File: main.py — POST /api/patients
  Problem: Any unauthenticated request can create patients. No token required.
           The blueprint explicitly states role-based access at API level.
  Fix: Add Depends(get_current_user) to all patient, appointment, and medical
       record endpoints.

BUG 5 — STATS ENDPOINT HAS NO AUTH GUARD
  File: main.py — GET /api/stats
  Problem: Dashboard stats (revenue, patient counts) exposed publicly with no token.
  Fix: Add authentication dependency.

BUG 6 — BROKEN MONTH CALCULATION IN /api/stats
  File: main.py — lines 97-108
  Problem: Month calculation uses timedelta(days=30*i) which is inaccurate.
           "6 months ago" calculated as 180 days will sometimes land in the wrong
           month (e.g., subtracting 180 days from March 1 gives September, but
           6 calendar months back is September — sometimes it's off by a month).
  Fix: Use dateutil.relativedelta or Python calendar arithmetic.

BUG 7 — CORS ALLOWS ONLY LOCALHOST
  File: main.py
  Code: allow_origins=["http://localhost:5173"]
  Problem: When deployed to production VPS, the frontend will be at a real domain.
           CORS will block all browser requests to the API.
  Fix: Load allowed origin from environment variable.

BUG 8 — NO RATE LIMITING ON LOGIN
  File: main.py — POST /api/auth/login
  Problem: Blueprint specifies "5 failed logins → lockout". Current implementation
           has zero rate limiting. An attacker can try millions of passwords.
  Fix: Use slowapi library or a Redis-backed counter for failed attempts per IP.

BUG 9 — DELETE PATIENT IS HARD DELETE
  File: main.py — DELETE /api/patients
  Problem: Deletes the patient record permanently from the database. In a medical
           system, patient records must be retained (legal requirement, typically
           5-10 years). A cascade delete here would also delete appointments,
           invoices, EMR records, and prescriptions — financial and clinical data.
  Fix: Add is_active = False soft delete. Never hard delete patient data.

BUG 10 — 2FA (TOTP) IS NOT IMPLEMENTED
  File: auth.py, models.py
  Problem: totp_secret field exists in the users table but the login endpoint
           never checks it. 2FA is completely bypassed. Blueprint says doctors
           and admin must use TOTP 2FA. Currently anyone who gets the password
           gets full access.
  Fix: Implement TOTP verification step in login flow using pyotp library.

BUG 11 — APPOINTMENT CONFLICT NOT CHECKED
  File: main.py — POST /api/appointments
  Problem: No check for overlapping appointments. Doctor can be double-booked.
           Patient can have two appointments at exact same time.
  Fix: Query for existing appointments for same doctor + overlapping time window
       before creating new one.

BUG 12 — INVOICE line_items FIELD MISSING FROM MODEL
  File: models.py
  Problem: Blueprint schema shows invoices.line_items as a JSONB array (what was
           actually billed — service name, quantity, unit price). The current
           Invoice model only stores subtotal/total as a single number. You cannot
           tell from the invoice what services were charged.
  Fix: Add line_items = Column(JSON) to Invoice model. Add LineItem schema.

PART 6: INDUSTRY STANDARD FEATURES NOT IN BLUEPRINT AT ALL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Based on research into leading physiotherapy CMS platforms (WebPT, SPRY, PhysioCare
PMS, Rehab Guru, AeglePro, PtEverywhere, MERIDIQ, Pabau), here are standard
features that real clinics need that are NOT mentioned anywhere in the blueprint
or codebase:

CLINICAL (HIGH PRIORITY):
  1. OUTCOME MEASURES / FUNCTIONAL ASSESSMENTS
     Real physio clinics use standardized outcome tools: VAS (Visual Analogue Scale
     for pain), NDI (Neck Disability Index), KOOS (Knee injury Outcome Score), DASH
     (Disabilities of Arm/Shoulder/Hand), ODI (Oswestry Disability Index).
     Without these, you cannot measure whether treatment is actually working.

  2. SESSION PROGRESS TRACKING PER EXERCISE
     Each physiotherapy session should record: exercise performed, sets completed,
     reps completed, resistance level, pain level before/after, patient compliance.
     The current model just stores free-text SOAP notes.

  3. BODY DIAGRAM / PAIN MAPPING
     Industry standard: an interactive body diagram where the doctor marks the
     location of pain/injury. Commonly done with a canvas overlay on a body SVG.

  4. PHYSIOTHERAPY-SPECIFIC ASSESSMENT FORMS
     ROM (Range of Motion) measurements in degrees per joint. MMT (Manual Muscle
     Testing) grades 0-5. Posture assessment. Neurological screening. Special tests
     (Lachman, McMurray, SLR, etc.). These are completely absent.

  5. HOME EXERCISE PROGRAMME (HEP)
     Doctors prescribe exercises for patients to do at home. The system should
     have an exercise library (with instructions + images/video links) and the
     ability to generate a printed HEP sheet or send it to patient via WhatsApp.

  6. SESSION PACKAGE MANAGEMENT
     Physiotherapy typically sold in packages (e.g., "10 sessions for PKR 15,000").
     No package model exists. Clinics need to track how many sessions remain in a
     purchased package and flag when a patient is running out.

OPERATIONS (HIGH PRIORITY):
  7. PATIENT CHECK-IN / WAITING ROOM
     A simple "today's queue" view showing which patients have arrived, who is
     with the doctor, and who is waiting. Receptionist marks patient as Arrived
     when they come in. This is a daily-use feature that's completely missing.

  8. APPOINTMENT CONFIRMATION FLOW
     Patient books → system sends confirmation → patient can confirm/cancel →
     if cancelled, slot opens → waitlist notified. This multi-step flow is
     standard but not implemented.

  9. DOCTOR AVAILABILITY / WORKING HOURS
     Doctors have set working hours. Appointments cannot be booked outside those
     hours. Currently there is no constraint at all on booking time.

  10. SERVICE CATALOG / FEE SCHEDULE
      A list of services with standard prices (Initial Assessment: PKR 1,500,
      Follow-up session: PKR 800, Dry Needling: PKR 500, etc.). Without this,
      every invoice requires manual price entry and there's no standardization.

  11. CONSENT FORMS
      Digital consent forms that patients sign (data storage consent, treatment
      consent, photography consent). In a medical setting this is a legal requirement.
      Blueprint mentions "patient consent recorded" in security section but there is
      zero implementation.

  12. PATIENT RECALL SYSTEM
      When a patient completes their treatment plan, the system should schedule
      a follow-up reminder (e.g., "check in with patient in 3 months"). This is
      a revenue retention feature AND a clinical best practice.

  13. MULTI-BRANCH SUPPORT
      If Rehab Swat ever opens a second location, the system should be ready.
      Currently there is no concept of clinic branches in the data model.

  14. TAX / GST SUPPORT
      Invoices need to show tax calculations if applicable. No tax fields exist.

  15. EXPENSE TRACKING

      Even in Pakistan, some employers have medical panels. The ability to mark
